# Инкассация и независимая загрузка фото — локальный кандидат, 2026-11-04

Статус: локальный кандидат; владелец согласовал проверку и выпуск. Не выпущено. Отдельное разрешение на production-миграцию запрошено. База production и
AIAgentAPI этим кандидатом не менялись. Исходная база кода d033d96 / runtime1.21.22.
Ветка codex/encashment-intent-photo-split-20261104.

## Согласованное поведение

- Новая фактическая передача той же суммы разрешена. Повтор запроса остаётся
  исходной операцией с тем же UUID. При устаревшем параллельном черновике
  сохраняется уточнение существующей/ещё одной передачи; сумма не служит ключом.
- После снимка исходный файл сохраняется в IndexedDB. Маленький запрос фиксирует
  сумму, направление, исходную смену и идентичность фото. Защищённое проведение
  РКО/ПКО начинается независимо от передачи фото; preview/confirm не удалены.
- Оригинал без сжатия передаётся фрагментами512KiB. После обрыва повторяются
  только неподтверждённые части. Полное фото подтверждается по размеру и SHA256.
  Частичное подтверждение суммы не удаляет исходник с телефона.
- Другие задачи доступны после подтверждения сохранения суммы. Компактное
  сообщение о фото снимается только после полного подтверждения файла.
- ADMIN отдельно видит финансовое состояние и отсутствие фото, в том числе
  в свёрнутой строке инкассаций. Существующий просмотр оригинала сохранён.
- При отказе IndexedDB используется фото-first multipart с тем же ключом,
  baseline и проверкой оригинала. Старые multipart-клиенты поддерживаются.
- Новая запоздавшая операция закрытой смены остаётся на решении ADMIN.
  Дозагрузка фото ранее принятой операции допустима после закрытия смены.
- Автоматический повтор финансовых ошибок по таймеру НЕ включён. Истёкшая
  первоначальная обработка доступна для явного решения ADMIN; дата загрузки
  фото не продлевает финансовую блокировку. Поздний ответ не перезаписывает
  более новое ручное состояние.

## До возможного выпуска

Аддитивная миграция добавляет4 nullable-поля CashOperation. Проверена отдельно
на локальной схеме до изменения; production-миграция не выполнялась. Перед
выпуском нужны визуальное согласование владельца, точная проверка истории
production-миграций и обычный release/version gate. Полная установка всей
старой цепочки миграций на пустую базу наткнулась на существующую ошибку
20260830143000_terminal_fiscal_review_responses (таблица ещё не создана);
этот исторический SQL в данной задаче не менялся.

В новом runtime предусмотрен аварийный переключатель CASH_OPERATION_METADATA_FIRST_ENABLED=0: новые передачи отправляются фото-first, уже сохранённые v2-очереди продолжают дозагрузку. Сервер сохраняет поддержку обоих протоколов. Переключатель не отключает защиту по исходному UUID. В штатном согласованном режиме значение1.

Откат: старый runtime1.21.22 не понимает отдельное подтверждение фото. После
появления v2-операций нельзя откатывать API на старую фото-first версию с
ожидающими фото; нужен совместимый резерв с поддержкой attachment-протокола
или завершение очередей до старого отката. Это обязательный gate подготовки
выпуска; кандидат не объявлен готовым к немедленному production-деплою.

Изменения payroll, OFD/matching, графика, нижней навигации и шаблонов чек-листов
не входят в задачу. Старые грязные рабочие деревья не изменялись. node_modules
и Prisma изолированы от прежних работающих локальных демонстраций.
