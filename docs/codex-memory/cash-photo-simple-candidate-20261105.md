## Результат и границы

- Фото, сумма, исходный день и РКО/ПКО связаны одним неизменным UUID и hash/size
  оригинала. Разделены сетевые этапы, не бизнес-операция и не история.
- Только фото инкассации:64МиБ вместо8МиБ, без сжатия/уменьшения исходника.
  JPEG/PNG/WebP проверяются по заголовку; поддержаны пустой MIME камеры,
  image/jpg и application/octet-stream при настоящем совместимом заголовке.
  Прочие вложения/чек-листы сохраняют прежние8МиБ и строгую проверку MIME.
- Только cash input запрашивает image/jpeg,image/png,image/webp вместо image/*.
  WebKit описывает автоматический выбор совместимого представления HEIC из
  Photo Library при явно ограниченном accept:
  https://bugs.webkit.org/show_bug.cgi?id=292350,
  https://bugs.webkit.org/show_bug.cgi?id=267277.
  Это не результат теста физического iPhone. RAW/произвольный HEIC через Files
  и файлы выше64МиБ не заявлены как поддержанные. Портал сохраняет ровно те
  байты, которые передал браузер, без собственного перекодирования.
- После проверенной записи в IndexedDB форма закрывается; короткий intent
  отправляет сумму/идентичность фото отдельно. Тот же photo outbox немедленно
  запускает передачу512КиБ частей, не ожидая окончания долгого1С POST.
- Денежный guard принадлежит только стадии неизвестного intent. Фото уже
  принятой операции не мешает новой фактической передаче той же суммы.
  Baseline ID, подтверждение разных физических передач, серверная блокировка
  и прежняя защита legacy не отменены. Старое завершение фото не может снять
  блокировку более нового денежного запроса или сбросить его форму.
- Photo worker по-прежнему один; новый принятый снимок подхватывается сразу
  после завершения предыдущего. Сбой фото одной принятой операции не держит
  фотографии других принятых операций. Финансовая неопределённость продолжает
  защищаться прежним образом; автоматического перепроведения ошибок1С нет.
- Обычная передача/обрыв/повтор показывают ОДНУ нейтральную строку:
  «Фото сохранено на телефоне / Отправим автоматически». Офлайн добавлено
  короткое «Нет связи». Технические ошибки не требуют ручного повтора и не
  превращают работу сотрудника в набор заявок/пушей. После точного photo receipt
  строка исчезает. Короткое подтверждение использует прежний4-секундный toast.
- Настоящий отказ хранения первого снимка остаётся видимым. RAM-only нельзя
  называть надёжным сохранением. Прежнее предупреждение до помещения денег
  в сейф, удержание File, попытки сохранения даже без сети, beforeunload и
  запрет auto-update при таком файле сохранены. Никаких новых push/Telegram
  уведомлений или типов ADMIN-входящих не добавлено.
- ADMIN по-прежнему видит «Нет фото» в той же карточке инкассации, затем
  миниатюру/оригинал рядом с её документами. Финансовые ошибки не спрятаны.
- Сервер собирает большие фото в файл последовательно, не удерживая сразу
  несколько полных копий снимка. Проверяет полный SHA256/длину и атомарно
  сохраняет оригинал. Части удаляются только после DB commit, как прежде.

## Реальный визуальный показ

С наступлением5 ноября создан новый synthetic день, старые6 операций4 ноября
и их фото сохранены. Никакие реальные сотрудники/кассы не использовались.

- PWA: http://localhost:3223/employee (порт3221 также использует новую сборку).
- ADMIN: http://127.0.0.1:3221/admin/workday?date=2026-11-05&control=all&employee=1.
- В первой передаче принято12582924 байта тестового PNG (12МиБ), без8МиБ-ошибки.
  Форма закрылась после local receipt. При задержке3сек на часть открыта новая
  форма и принята ещё одна передача40000 с другим UUID, пока первое фото шло.
- Оба финансовых результата posted_1c_pair, по40000. Фото получены с исходными
  байтами и SHA256. Большое фото действительно отображается в ADMIN1480x2100,
  рядом с LOCAL-RKO-13/LOCAL-PKO-13. Второе относится к отдельной паре.
- Прервано соединение, при этом оставалась спокойная строка о сохранённом фото.
  Связь возвращена: остаток фото дошёл автоматически, строка исчезла без кнопки.
- Доказательство: /tmp/mobo-cash-simple/evidence.json.
- Снимки: /tmp/mobo-cash-simple/01-accepted-background.jpg,
  02-offline-saved.jpg,03-sent.jpg,04-admin-linked-photo.jpg.

Стенд использует прежний изолированный proxy/симуляцию памяти и сети3223 и
локальную заглушку1С3222. После показа все fault-флаги false, chunk delay100мс.
Тестовые изображения — печатная QR-форма и тот же PNG с большим корректным
ancillary tEXt chunk; это не настоящие деньги/не доказательство теста камеры.
Физический iPhone, его Photo Library/camera, выгрузка iOS и настоящая слабая
мобильная сеть остаются НЕ ПРОВЕРЕНЫ. Ограничения browser persistence сохраняются.

## Выпуск и откат

После реального локального показа Бэла разрешила выпуск: «Хорошо, выпускай.
Только проверь перед выпуском, чтобы ничего уже настроенное не сломалось.
Потом проверю на телефоне». Установка выполнена в1.21.30, новые DB поля не добавлялись. При будущем выпуске сохранять production env/volumes/документы,
перечитать runbook, проверить live/deploy version и параллельные изменения.
Обычные запросы фото остались512КиБ, JSON16КиБ; repo Traefik labels не добавляют
body-buffering limit. Emergency photo-first путь проверен напрямую HTTP с12МиБ;
не менять его переключатель без отдельной операционной необходимости.

После появления ожидающих фото больше8МиБ нельзя откатывать API на прежнюю
валидацию8МиБ. Нужен совместимый резерв с64МиБ/attachment-протоколом или
завершение ожидающих фото до такого отката. Старый API может сохранить сумму,
но отвергнуть завершение большого фото; original на телефоне не удалять.
