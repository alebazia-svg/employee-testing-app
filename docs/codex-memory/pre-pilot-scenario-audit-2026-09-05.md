# Предпилотный сценарный аудит портала

Дата начала: 2026-09-05.

## Назначение

До выдачи PWA реальным сотрудникам проверить рабочий день в изолированном QA
на синтетической команде: два сотрудника Розницы, один сотрудник Опта и один
администратор. Production, реальные сотрудники и реальные документы 1С в этом
прогоне не изменяются.

Статусы:

- `PASS AUTO` — подтверждено автоматическим тестом;
- `PASS QA` — пройдено через реальное QA-приложение и изолированную QA-БД;
- `DEVICE` — окончательно проверяется владельцем на iPhone;
- `DRILL` — требуется управляемая имитация отказа;
- `BLOCKED` — обнаружен предпилотный дефект;
- `PENDING` — ещё не выполнено.

## Текущие блокеры до ручного iPhone-прогона

Блокирующих кодовых дефектов из этого прогона не осталось. Перед выдачей PWA

## Найденные несогласованности

1. `RESOLVED` в `6af0185`: текст ошибки закрытия ККМ теперь прямо говорит об
   автоматической повторной проверке и не предлагает несуществующую кнопку.
2. `RESOLVED` в `6af0185`: запрос технического завершения нельзя отправить без
   выбранной причины и непустого комментария; серверная проверка сохранена.
3. `RESOLVED` в `6af0185`: ADMIN использует точный сохранённый результат
   изолированного Dev/Test-сценария ККМ, а проверки со статусом `attention`
   больше не соседствуют с ложным верхним сообщением «Всё нормально».
4. `PASS QA`: в техническом завершении выбор причины без комментария не
   активирует отправку; после заполнения обоих полей запрос появился у ADMIN.

## Наблюдение для следующего UX-разбора

2026-09-05 владелец заметил на реальном общем задании по отсутствующему чеку:
первый открывший сотрудник получает 15-минутную блокировку, а остальные видят
«Уже проверяет: имя сотрудника». Это защита от одновременной двойной работы, а не
определение владельца оплаты. Формулировка может ошибочно восприниматься как
утверждение, чей это чек, и удержать фактического владельца от исправления.

К пилотному наблюдению, без изменения в текущем пакете: отдельно оценить
нейтральную формулировку блокировки и безопасный способ для фактического
владельца забрать проверку. Не определять владельца только по тому, кто первым
открыл карточку, и не убирать защиту от параллельных действий без проверки
конкурентных сценариев.
